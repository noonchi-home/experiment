# Claude 검토와 수정 의견 (3단계)

> **확인 범위**
> - 요청에 포함된 Codex 후보안(02)과 검토문(06) 본문만 읽었습니다. 외부 검색, 원문 대조, API 실행은 하지 않았습니다.
> - Codex가 공식 기록으로 확인했다고 밝힌 수상과 수치(PARTNR, 에이전트 확장 연구, ContextAgent·ProAgent 포함)는 다시 확인하지 못했습니다. 다만 제 기억과 분명히 어긋나는 항목은 없습니다.
> - 관측 가치 예시(1.9 / 2.4 / 3.9)는 직접 다시 계산해 맞음을 확인했습니다. 관측 결과별 정책도 사후확률 약 0.84 / 0.13 기준에서 최적입니다.
> - 실행 환경의 모델은 claude-opus-5-5로 표시되지만 effort 설정은 제가 확인할 수 없습니다.

## 1. Codex 후보안 검토 — 결론: 수정 필요

**유지할 강점**
- 다음 네 가지를 나눈 것이 좋습니다: 장치 상태, 사람의 활동 해석, 시스템의 목표, 행동 정책.
- '선제적'을 "명령 없이 스스로 개입"과 "미래를 예측해 예방" 두 의미로 나눈 것은 제 초안보다 낫습니다.
- "관찰만으로는 구분할 수 없는 경우가 있다"는 지적도 정확합니다.
- 다음 설계들도 유지할 가치가 있습니다.
  - 관찰마다 출처, 관찰 시각, 도착 시각, 오래됨·충돌 여부를 표시
  - 저장된 기록 조회와 새 관측을 구분
  - 명령의 요청·확인·실패 상태를 구분
  - 숨은 실제 상태를 가진 시뮬레이터
  - 정답을 행동 하나가 아니라 '허용 행동 집합'으로 채점
  - 아무 개입도 필요 없는 긴 구간 포함

**실질적 약점**

1. **최종 행동을 누가 고르는지, 무엇을 모델 밖에서 보장하는지가 비어 있습니다.**
   - 기준선은 '단일 API 모델 + 상태 관리 + 전제조건 확인'입니다. 그런데 입력에 들어 있는 '허용 범위'를 모델이 읽고 지키는지, 코드가 검사하는지는 정하지 않았습니다.
   - Codex가 제 안에 대해 든 반례(수면 확률을 낮게 추정해 잘못 청소)는, 모델이 직접 행동을 고르는 이 기준선에서 더 직접적으로 일어납니다.
   - 예: 밤에 안방 재실 센서가 켜져 있어도 모델이 "깨어 있다"고 추정하면 막을 장치가 없습니다.
   - API가 응답하지 않을 때의 대체 정책도 "시험한다"고만 했고, 구조 안 어디에 두는지는 없습니다.
2. **API 답변이 실행할 때마다 달라질 수 있다는 점을 다루지 않습니다.**
   - 같은 입력을 반복했을 때 행동이 일관적인지 보는 지표가 없습니다.
   - 적은 에피소드로 여섯 조건을 비교하면, 조건의 효과와 우연한 차이가 섞입니다.
   - 위험 누락을 다른 오류와 합치지 않고 따로 보고한다는 원칙도 명시되지 않았습니다.
3. **보완 제안**
   - '추가 관측의 효용'은 지표 이름만 있고 판정 방법이 없습니다. 모델이 관측을 요청할 때 "결과가 A면 X, B면 Y"를 미리 적게 하면, 모든 결과에 같은 계획을 적은 요청을 자동으로 '불필요'로 판정할 수 있습니다.
   - 관측 비용에서 사생활(카메라)과 가족 사이의 선호 충돌이 빠졌습니다.
   - 여섯 비교 조건에 우선순위가 없습니다.

**판단이 바뀔 조건:** 첫 실험을 청소·창문 같은 저위험 과제로만 한정하면, 1번의 긴급도는 낮아집니다.

## 2. Codex의 다섯 지적에 대한 답

1. **가스 규칙 → 부분 수용**
   - 회의에서 구체 규칙을 정한 것은 과했습니다. 알림에 답이 없는 것이 못 들어서일 수 있다는 반례도 맞습니다.
   - 실제 동작은 장치 사양과 기존 안전 기준에서 받고, 합성 실험에서는 사양을 명시적인 입력으로 줍니다.
   - 다만 구조 원칙은 유지합니다: 위험 대응 경로는 모델 밖에 있고, 모델이 뒤집을 수 없으며, API 장애 때도 작동합니다.
   - '무응답이면 어떻게 하나'는 비워 둘 수 없는 칸입니다. 그래서 사양을 바꿔 가며(알림만 / 시간이 지나면 차단) 실험 변수로 둡니다.
2. **모델이 낸 숫자로 코드가 계산 → 수용**
   - 보정되지 않은 확률을 코드가 계산에 쓰면, 정밀해 보이기만 하는 오류가 됩니다.
   - SayCan을 '코드 승인'의 근거로 든 것도 과대 적용이었습니다. SayCan은 언어 점수와 학습된 실행 가능성을 결합하는 방식이지, 안전 승인 장치가 아닙니다.
   - 수정: 코드는 모델의 추정이 아니라 원래 관찰값과 주어진 사양으로만 검사합니다. 비용표로 최적 행동을 계산하는 방식은, 참 확률을 아는 합성 실험에서 비교 기준(상한)으로만 씁니다.
3. **첫 행동이 같아도 정보는 가치가 있음 → 수용**
   - 제 규칙은 바로 다음 한 단계만 본 기준이었습니다.
   - "판단 기간 안의 이후 단계까지 계획이 바뀌지 않으면 관측하지 않는다"로 고치고, 관측과 되돌릴 수 있는 행동을 동시에 하는 경우도 포함합니다.
4. **사용자가 되돌렸다고 곧 오판은 아님 → 수용**
   - 시각·맥락·대상이 담긴 피드백 기록으로 저장합니다.
   - 원인을 다섯 가지로 나눕니다: 최초 오판, 상황 변화, 선호 변화, 사용자 실수, 원인 불명. 검토를 거친 것만 학습에 씁니다.
   - 반대로, 되돌리지 않았다고 정답으로 확정되는 것도 아닙니다.
5. **파인튜닝과 실험 규모 → 부분 수용**
   - "로컬 모델이면 파인튜닝 우선", "LoRA 다음 DPO", "상황 유형 10개 안팎이면 규칙"은 근거 없이 고정한 경계라 철회합니다.
   - 시나리오 40~60개, 관측 3회, 반복 5회는 '처음 탐색용 예산'임을 명시합니다.
   - 다만 바로 시작할 수 있도록 구체적인 초기 예산을 적어 두는 것은 유지합니다.

## 3. Claude 수정 의견 (사용자께 보여드릴 내용)

가장 중요한 설계 결정은 "어떤 모델을 쓰느냐"보다 **"판단의 어느 부분을 AI 모델에 맡기고, 어느 부분을 모델 밖에서 보장하느냐"**라고 봅니다. 모델은 보이지 않는 상황을 해석하는 데 강합니다. 하지만 같은 입력에도 답이 흔들리고, 모델이 말하는 확신 숫자를 믿기 어렵습니다.

**역할 분담 (현재 권고)**

- **코드가 맡을 일**
  1. 사건 기록, 시각, 정보가 얼마나 최신인지 관리
  2. 행동마다 '허용 수준'(자동 실행 / 알림 후 실행 / 알림만 / 금지)을 둡니다. 이 수준은 장치 사양과 설치 때 정한 가정 정책이 정하고, 모델은 바꾸지 못합니다.
  3. 두 종류의 규칙을 둡니다.
     - **금지 규칙:** 잘못 실행하면 손해가 큰 행동을 막습니다. 예: 사양에 "밤에 사람이 있으면 청소 금지"가 있으면, 모델의 수면 추정이 아니라 재실 센서 값으로 검사합니다.
     - **독립 발동 규칙:** 행동하지 않으면 손해가 큰 상황에서 모델과 상관없이 작동합니다. 구체적인 동작은 장치 사양에서 받습니다.
  4. 명령 진행 상태, 관측 횟수와 시간 제한 관리
- **모델이 맡을 일**
  - 보이지 않는 상태에 대한 가설과 근거(어느 관찰에서 나왔는지 번호로 표시)
  - 후보 행동 제시(대기, 나중에 다시 확인하기 포함)
  - 허용된 행동 중 최종 선택과 그 이유
  - 판단을 다시 해야 할 조건
- **최종 선택 방식**
  - 모델이 허용 범위 안에서 고릅니다. 범위를 벗어나면 코드가 거부 이유를 돌려주고 다시 고르게 합니다.
  - 코드가 확률을 계산해 대신 고르지는 않습니다.
  - 한계: 코드 규칙은 사양이 옳은 만큼만 옳습니다.

**추가 관측을 고르는 방법**
- 먼저 "이 정보가 지금이나 이후의 행동을 바꿀 수 있는가?"를 묻습니다. 아니면 보지 않습니다.
- 바꿀 수 있으면 비용이 싼 것부터 씁니다.
  1. 저장된 기록 조회
  2. 이미 있는 센서 읽기
  3. 카메라·로봇 이동
  4. 사용자 알림 (마지막 수단)
- 비용에는 시간, 방해, 사생활, 관측 실패 가능성이 모두 들어갑니다.
- 급하면 되돌릴 수 있는 행동과 관측을 동시에 합니다.
- 모델은 관측을 요청할 때 "결과별로 다음에 무엇을 할지"를 함께 적습니다.

**첫 실험**
- 시뮬레이터가 실제 상태를 숨기고 있다가, 모델이 요청한 관측만 알려줍니다. 시나리오마다 장치 사양과 허용 수준을 명시합니다.
- 비교 순서:
  1. 추가 관측 요청 불가 vs 가능
  2. 현재 값만 vs 시간 기록 포함
  3. 모델 단독 선택 vs 모델 + 코드 허용 검사
  4. 참 확률을 아는 코드의 최적 선택 (합성 실험에서만 쓰는 비교 기준)
- 추론 모드, 검토 호출 추가, 역할 분담 비교는 그다음입니다.
- 평가 지표:
  - 위험 누락 (따로 보고)
  - 개입이 필요 없는 긴 구간에서 시간당 불필요한 개입
  - 불필요하거나 빠뜨린 관측
  - 코드가 거부한 비율 (모델이 규칙을 이해하는지 확인)
  - 같은 입력을 반복했을 때의 일관성
  - 응답 지연

**멀티에이전트·파인튜닝**
- 실패 원인을 본 뒤 정합니다.
- 정보가 없어서 틀린다면 학습이 아니라 관측 도구와 상태 표현을 고칩니다.
- 로컬 모델에서 답변 형식, 도구 호출, 일관성 문제가 반복되면 검토된 기록으로 파인튜닝을 검토합니다.
- 모델 호출을 늘리는 것은 같은 비용에서 특정 실패를 줄이는 경우에만 합니다.

**Codex 안과 남는 차이**
- 저는 세 가지를 첫 실험부터 넣자는 입장입니다.
  1. 코드 허용 검사를 비교 조건에 포함
  2. 결과별 계획을 미리 적게 해서, 확률 없이도 관측이 쓸모 있었는지 채점
  3. 반복 일관성 측정과 위험 누락 별도 보고
- 다음은 Codex 안을 받아들였습니다: '선제적'의 두 의미 구분, 입력 정보 표시 방식, 명령 상태 구분.

**아직 정하지 않은 것**
- 가스 같은 위험 상황에서의 실제 동작 (장치 사양 필요)
- 행동별 허용 수준
- 모델이 내는 확률을 쓸지 여부 (보정 결과에 따라)
- '예측형 선제'를 첫 실험에 넣을지
- 최종 모델, 에이전트 수, 파인튜닝 여부
- 신뢰성을 주장할 수 있는 평가 규모
