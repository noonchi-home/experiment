# 선제적 가정 AI 의사결정: Claude 독립 의견 (회의용 초안)

> 외부 검색은 하지 않았고 논문 원문과 프로젝트 파일도 읽지 않았습니다. 아래 내용은 기억을 바탕으로 썼습니다. 실행 환경에는 모델이 claude-opus-5-5로 표시되지만, effort 설정값은 제가 직접 확인할 수 없습니다.

## 1. 문제의 성격
이 문제는 '상황 → 행동' 표에서 답을 찾는 일이 아닙니다. **지금 요리 중인지처럼 센서로 바로 보이지 않는 사실을 추정해야 합니다. 동시에 잘못 판단하면 한쪽 피해가 훨씬 큰 상황에서 '행동, 추가 관측, 알림, 대기' 가운데 하나를 골라야 합니다.**
- 학계 용어로는 POMDP(집안 상황을 모두 볼 수 없을 때, 현재 상태를 추측하면서 행동하는 틀)입니다.
- 또 하나는 정보의 가치(더 알아보는 이득이 그 비용보다 큰가)입니다.
- 말씀하신 '추가 데이터가 필요한지 스스로 판단하는 내부 결정'이 바로 이 문제의 핵심입니다.

판단 기준은 네 가지입니다.
- 보이지 않는 상태가 얼마나 불확실한가
- 잘못 판단했을 때 피해가 양쪽으로 얼마나 다른가: 요리 중 가스를 끄면 불편하고, 방치된 가스를 안 끄면 화재 위험이 있습니다.
- 얼마나 급한가
- 행동을 되돌릴 수 있는가

"요리 중이면 가스를 끄지 않는다"도 절대 규칙은 아닙니다. 불꽃 없이 가스만 새거나 사람이 오래 자리를 비웠다면 요리 중이어도 개입해야 합니다. 판단 대상은 '가스가 켜져 있음'이 아니라 '가스가 위험한 상태'입니다.

## 2. 필요한 정보 (사용자 입력 없이)
- **현재 상태**: 가스 밸브·불꽃·화구 온도, 창문, 청소기, 가스·일산화탄소·연기 농도, 방별 먼지, 비 감지
- **시간 흐름**: 켜져 있던 시간(가스 42분), 변화 추세(냄비 온도 상승), 사람이 마지막으로 감지된 시각
- **사람**: 방별 재실 여부, 추정 활동(요리·수면·외출), 아이·노인 여부, 평소 생활 패턴
- **외부**: 일기예보, 바깥 미세먼지, 시각
- **기기 행동**: 가능한 행동, 부작용, 실행 조건(예: 누가 자고 있을 때 소음)
- **가정 정책**: 설치할 때 한 번 정함(예: 가스는 경고 우선)
- **물체 기억** (컵 예시): 물체별로 무슨 일이 있었는지 기록

센서 숫자를 그대로 모델에 넣기보다 '사건 기록 + 요약 정보'로 바꿔 넣기를 권합니다. LLM이 긴 숫자 나열에 약하다는 것은 제 판단이므로 실험으로 확인해야 합니다.

## 3. 더 볼지, 바로 행동할지
1. 추가로 확인한 결과가 무엇이든 결정이 같으면 → 바로 행동
2. 확인 결과에 따라 결정이 바뀌고, 기다려도 안전하면 → 추가 확인
3. 급하면 → 되돌릴 수 있는 안전한 행동 먼저 (창문은 즉시 닫고, 가스는 경고 후 반응이 없으면 차단)
4. 센서로 알 수 없는 사람의 의도가 걸려 있고 피해가 크면 → 알림. 사용자에게 묻는 것은 '가장 비싼 확인 수단'으로 보고 위험할 때만 사용

예시: 가스가 42분째 켜져 있고, 주방에 35분째 아무도 없고, 냄비 온도가 오르고 있습니다. 방치일 수도 있지만 사골처럼 일부러 오래 끓이는 중일 수도 있습니다. 그래서 바로 차단하지 않고 경고를 보낸 뒤 반응이 없으면 차단합니다.

추가 확인의 비용에는 시간뿐 아니라 카메라 같은 사생활 침해도 들어갑니다. 행동 목록에는 '아무것도 안 함'과 '몇 분 뒤 다시 확인'을 반드시 넣어야 합니다. 선제형 비서가 흔히 실패하는 이유는 불필요하게 끼어들어 신뢰를 잃는 것입니다.

## 4. 권하는 구조 (확정 아님)
- **0층 안전 규칙 (코드)**: 가스·연기 농도가 기준을 넘으면 즉시 차단합니다. LLM이 뒤집을 수 없고, API 응답이 늦어도 작동합니다.
- **1층 해석 (LLM)**: 보이지 않는 상태를 추정하고 근거와 확신 정도를 적습니다.
- **2층 제안 (LLM)**: 후보 행동마다 기대 효과, 틀렸을 때의 피해, 되돌릴 수 있는지를 적습니다.
- **3층 승인 (코드)**: 피해 비용표와 규칙으로 최종 행동을 고릅니다.
- **4층 피드백**: 사용자가 되돌린 행동(예: AI가 끈 가스를 다시 켬)을 오판 기록으로 저장합니다.

사용자께서 제시한 4단계 틀(인지, 평가, 의사결정, 실행·피드백)과 대체로 맞습니다. 다른 점은 두 가지입니다. 안전 규칙을 맨 앞에 따로 두었고, 의사결정을 'LLM이 제안하고 코드가 승인'하는 두 단계로 나눴습니다.

## 5. 첫 DeepSeek 실험
- **시나리오**: 합성 시나리오 40~60개를 JSON으로 만듭니다. 정답은 사람이 미리 정합니다. 같은 LLM이 시나리오와 정답을 만들면 스스로 채점하는 꼴이 되기 때문입니다.
- **비교 쌍**: 가스가 켜진 것은 같고 재실 여부나 온도 추세만 다른 쌍을 만듭니다. 모델이 증거를 보고 판단하는지, '가스 켜짐 → 끄기' 패턴만 외웠는지 구분할 수 있습니다.
- **충돌·잡음 상황**: 비가 오는데 요리 연기 때문에 환기가 필요한 경우, 바깥 미세먼지가 심한데 환기가 필요한 경우, 안방에 먼지가 많은데 누가 자는 경우, 센서끼리 결과가 다르거나 값이 빠진 경우
- **추가 확인 반복**: 모델이 요청한 값을 시뮬레이터가 알려줍니다 (최대 3회).
- **비교할 방식**: ① 바로 답하게 하기 ② 정해진 양식에 맞춰 답하게 하기 ③ LLM은 확률과 비용만 내고 결정은 코드가 하기. 추론 모드를 켰을 때와 껐을 때도 비교합니다 (현재 제공 모델명은 확인 필요).
- **평가 지표**:
  - 위험을 놓친 경우 (따로 세고 가장 중요하게 봄)
  - 불필요하게 개입한 경우
  - 필요 없는 확인을 하거나 필요한 확인을 빠뜨린 경우
  - 같은 입력을 5번 넣었을 때 결과가 일관적인지
  - 관계없는 정보를 넣었을 때 판단이 흔들리는지
  - 모델이 말한 확신 정도와 실제 정답률의 차이

## 6. 멀티에이전트·파인튜닝·모델 변경 (제 판단)
- **지금은 셋 다 이릅니다.** 어떤 실수를 하는지 모르는 상태에서 파인튜닝하면 근거 없는 투자가 됩니다.
- **멀티에이전트**: 역할을 나누는 것은 유용하지만 LLM을 여러 개 둘 필요는 없습니다. 별도의 '안전 검토' 호출이 위험 누락을 실제로 줄일 때만 추가합니다. LLM 여러 개가 토론하는 방식은 비용과 지연이 커서 뒤로 미룹니다.
- **파인튜닝**: 로컬 소형 Qwen으로 옮길 때 필요할 가능성이 큽니다. 순서는 이렇게 권합니다.
  1. 검증된 판단 기록으로 일부만 가볍게 추가 학습 (LoRA)
  2. 더 나은 판단과 못한 판단을 비교하며 학습 (DPO 등)
- **모델 구조 변경**: 거의 필요 없습니다. 예외는 센서 값을 촘촘한 간격 그대로 직접 읽어야 할 때 붙이는 시계열 처리 모듈입니다.

## 7. 참고 논문 (원문 미확인)
표기: [확실]은 논문이 존재하고 게재처가 맞다고 기억상 확신한다는 뜻입니다. 수상 정보와 세부 수치는 모두 외부 확인이 필요합니다.

1. **Kaelbling·Littman·Cassandra (1998, Artificial Intelligence 저널), POMDP**
   - 가져올 아이디어: 현재 상태를 추측하며 판단하는 틀, 정보를 더 모으는 행동의 가치
   - 한계: 문제가 커지면 정확한 계산이 불가능
   - [확실]
2. **Horvitz, "Principles of Mixed-Initiative User Interfaces" (CHI 1999)**
   - 가져올 아이디어: 사용자 목표의 확률에 따라 '자동 행동 / 확인 / 아무것도 안 함'의 경계를 이득·손해로 정함. 우리 문제와 가장 직접적으로 맞닿아 있음
   - 한계: PC 비서 환경을 다룸
   - [확실, 수상 여부 모름]
3. **ReAct (ICLR 2023)**
   - 가져올 아이디어: 생각, 행동, 관찰을 반복하는 방식으로 '추가 확인' 반복 구조의 기본형
   - 한계: 비용이나 불확실성 개념이 없음
   - [확실]
4. **SayCan (CoRL 2022)**
   - 가져올 아이디어: LLM이 판단한 '유용성'과 별도 모델이 판단한 '실행 가능성'을 곱해 선택. 3층 승인의 근거
   - 한계: 따로 학습시킨 실행 가능성 평가 모델이 필요
   - [확실]
5. **KnowNo, "Robots That Ask For Help" (CoRL 2023)**
   - 가져올 아이디어: 컨포멀 예측(통계적 보정)으로 확신이 부족할 때 도움을 요청
   - 한계: 보정용 데이터와 객관식 형태의 선택지가 필요
   - [확실, CoRL 최우수 학생논문상으로 기억하지만 확인 필요]
6. **Generative Agents (UIST 2023)**
   - 가져올 아이디어: 최근성, 중요도, 관련성을 기준으로 기억을 꺼내는 방식. 물체별·시간별 기록 요약에 참고
   - 한계: 안전 판단을 검증한 연구는 아님
   - [확실, 수상 기억 불분명]

AlphaGo·MuZero 같은 유명한 강화학습은 규칙이 분명한 환경에서 엄청난 횟수의 시행착오를 거쳐야 해서 첫 단계에는 맞지 않습니다. '상 받은 정답 논문'을 찾기보다 우리 문제와 구조가 맞는 논문을 고르는 것이 중요합니다.

## 8. 추천이 바뀔 조건
- 상황 유형이 10개 안팎으로 고정되면 → 규칙과 확률표가 더 안정적이고, LLM은 설명용으로만 사용
- 프롬프트를 고쳐도 위험 누락이나 결과 불일치가 남으면 → 결정을 코드 쪽으로 더 옮기거나 파인튜닝
- 로컬 소형 모델이 필수가 되면 → 파인튜닝을 우선
- 여러 기기와 가족 구성원의 목표 충돌이 커지면 → 멀티에이전트 검토
- 센서 숫자를 그대로 해석해야 하면 → 시계열 처리 모듈 추가
