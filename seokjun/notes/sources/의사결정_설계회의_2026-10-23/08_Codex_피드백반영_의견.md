# Codex 수정 의견 — Claude의 실제 피드백 반영

작성일: 2026-10-23. Claude Opus 5.5의 독립 의견과 003 교차 검토 응답을 읽고 작성했다. 최종 제품 설계를 확정하거나 실제 API 실험을 수행한 것은 아니다.

## 1. 내가 유지하는 제안

첫 비교 대상은 **명시적인 상태·기억 + 한 개의 API 판단 모델 + 실제 결과를 돌려주는 관찰·행동 도구 + 모델 밖의 실행 관리**다. 어려운 부분은 상황을 설명하는 문장을 만드는 데서 끝나지 않는다. 시스템이 무엇을 모르는지, 그 정보를 알면 무엇이 달라지는지, 지금 실행할지 기다릴지, 실행 결과에 따라 언제 판단을 바꿀지를 시험해야 한다.

관찰과 실제 상태, 사람의 활동과 시스템의 목적을 나누는 기존 설명은 유지한다. 또한 명령 없이 개입하는 선제성과 미래를 예상해 예방하는 선제성을 구분한다. 첫 실험에서 둘을 모두 달성했다고 주장할 필요는 없다.

## 2. Claude의 지적으로 명확히 고친 부분

**모델과 코드의 책임을 명시한다.** 기존 초안에도 최신 상태·전제조건 검사는 있었지만 누가 어느 범위까지 수행하는지가 충분히 분명하지 않았다. 따라서 ‘검사가 전혀 없었다’는 평가는 부분적으로만 수용하고, 책임 분담의 명료화는 수용한다.

| 역할 | 첫 실험에서 맡길 책임 |
| --- | --- |
| 상태·실행 코드 | 관찰 출처·시각·대상, 충돌·오래됨·미관측, 실행 요청과 실제 결과 관리 |
| API 모델 | 상황 가설과 근거, 후보 행동, 필요한 추가 관찰, 허용 범위 내 선택, 재검토 조건 제안 |
| 코드의 실행 검사 | 주어진 정책·기기 능력·인자·전제조건·시간 제한·중복·충돌 확인. 거부 이유를 기록 |
| 기기별 독립 대응 경로 | 외부에서 명시한 장치 정책에 해당하는 경우, API 응답에 의존하지 않는 동작 수행 |

가스의 실제 차단 조건이나 알림 후 무응답의 처리 방식을 이 문서에서 임의로 만들지는 않는다. 장치별 사양이 합성 실험의 입력이라면 그 사양에 따르는지를 시험할 수 있다. ‘코드로 구현함’, ‘원래 센서 값임’은 그 자체로 신뢰성의 증명이 아니다. 센서의 최신성·충돌·실패와 명세의 적용 조건도 다뤄야 한다.

**코드가 모든 가치 판단을 대신 계산한다는 뜻은 아니다.** 모델이 내놓은 검증되지 않은 확률·비용을 코드에 넣으면 오판을 정확하게 계산해 낼 수 있다. 처음에는 정책과 제약 안에서 모델이 선택하게 하고, 작은 합성 문제에서는 알려진 확률·효과·비용·판단 기간으로 계산한 정책과 비교하자. 이것을 최적 기준이라고 부르려면 해당 문제의 목표와 정보 조건 안에서 실제로 최적화했는지도 확인해야 한다.

**평가에 반복과 위험 구분을 추가한다.** 같은 모델 버전·설정·입력으로 반복했을 때 적절한 행동의 분포가 어떻게 달라지는지 보자. 허용되는 대안이 여러 개인 경우 문장이나 행동명이 다르다는 이유만으로 오답 처리하지 않는다. 일관되게 틀리는 모델도 있으므로 일관성은 정확성을 대신하지 않는다.

위험한 개입 누락은 일반적인 도움 누락과 따로 보고한다. 불필요한 개입은 평상시 구간의 길이를 고려한다. 코드의 거부 비율은 모델의 규칙 이해를 보는 진단 지표이지, 낮을수록 무조건 좋은 성능 지표는 아니다. 항상 아무 행동도 제안하지 않으면 거부율은 낮아져도 필요한 일을 놓칠 수 있다.

## 3. 추가 관측에 대한 내 기준

추가 관측은 ‘정보가 더 많아짐’보다 **정해진 판단 기간 안에서 행동과 결과를 얼마나 개선하는지**로 평가해야 한다. 비용에는 시간·자원·사생활·사용자 방해·관측 실패 가능성을 포함한다. Claude가 강조한 오판 피해의 비대칭과 행동을 되돌릴 수 있는지도 비교축으로 반영한다. 다만 되돌릴 수 있다는 이유만으로 행동이 적절해지는 것은 아니다.

‘저장 기록 → 센서 → 카메라 → 사용자’는 후보를 떠올리는 기본 순서일 수 있지만 필수 실행 순서는 아니다. 오래된 기록이 결정에 전혀 도움을 주지 않으면 바로 유효한 현재 센서를 선택하는 편이 나을 수 있다. 사용자를 매번 묻는 경로로 보내지 않되, 질문이 언제나 다른 모든 관측보다 나쁜 선택이라고 정의하지도 않는다.

모델에게 ‘결과가 A이면 X, B이면 Y’라는 계획을 미리 쓰게 하는 제안은 수용한다. 하지만 **그 글만으로 관측의 유용성을 판정하지 않는다.** 모델이 유용한 관측을 활용하지 못할 수도 있고, 쓸모없는 차이에 서로 다른 행동을 붙일 수도 있기 때문이다. 이 기록은 설명·오류 분석용으로 쓰고, 유효성은 사람이 검토한 기준이나 합성 환경의 결과 비교로 확인한다.

현재 첫 행동이 같아도 이후 분기가 달라지면 관측이 가치 있을 수 있다. 가능한 경우 관측과 행동을 병행하되, 자원·시간·장치 제약을 확인한다.

## 4. 첫 실험의 순서를 줄인다

내 이전 초안은 비교할 항목이 많고 우선순위가 약했다. 다음 세 가지를 우선 비교하는 제안을 채택한다.

1. **추가 관찰 불가 / 선택 가능:** 같은 이력·도구 조건에서 필요한 정보만 얻어 결과를 개선하는가.
2. **현재 상태만 / 시간 이력 포함:** 현재 장면은 같고 과거가 다른 사례를 구분하는가.
3. **모델 선택만 / 정책 검사 포함:** 합성 환경에서 어떤 위반을 막고 어떤 개입을 놓치는가. 실제 기기에서 보호 경로를 제거하는 시험은 아니다.

먼저 몇 개의 에피소드로 관찰→선택→환경 반응→재판단이 제대로 연결되는지 점검하고, 별도 평가 사례와 반복 실행으로 확장하자. 초기 사례 수와 관측 횟수는 탐색 예산이며 일반적인 신뢰성을 증명하는 기준이 아니다. 여러 변수를 동시에 바꾼 결과를 특정 구조 하나의 효과로 해석하지 않는다.

작은 계산 가능한 세계의 최적 정책, 좁은 규칙 기준선, 실제 API 판단을 같은 관측·행동·비용 조건에서 구분한다. 모델이 볼 수 없는 숨은 실제 상태를 아는 평가자는 별도로 둔다. 완전 정보 기준선은 참고 상한일 수 있지만, 부분 관찰 모델과 직접 동등한 경쟁 조건은 아니다.

## 5. 학습과 여러 에이전트는 언제 검토하나

정보가 없어서 틀리면 먼저 관측과 상태 표현을 고쳐야 한다. 상태를 알고도 반복적으로 잘못된 도구·행동을 고르면 프롬프트·계획 방식·검토 호출·미세조정을 비교할 근거가 생긴다. 여러 역할을 도입할 때는 추가 계산량의 효과와 역할 분담 자체의 효과를 분리한다.

로컬 Qwen을 쓴다는 사실만으로 미세조정이 필수는 아니다. 실제 로컬 모델에서 관측 선택·도구 사용·상태 유지·시간 지연이 어느 수준인지 먼저 측정하고, 검토된 기록과 별도 시험 데이터로 학습의 효과를 확인하자.

사용자가 되돌린 행동과 되돌리지 않은 행동을 곧바로 정답·오답으로 만들지 않는다. 상황·선호 변경이나 피드백 부재를 포함해 원인을 구분한 기록이 필요하다.

## 6. 아직 열어 둘 선택

모델 수, 최종 모델, 학습 여부, 기기별 정책, 관측 비용, 실제 가정의 신뢰성을 주장할 평가 규모는 미확정이다. 이번 회의에서 진전된 것은 **무엇을 비교하고 어떤 오류를 따로 봐야 하는가**다. 두 모델의 동의가 실제 시스템 실험을 대신하지 않는다.

근거 자료와 최초 의견은 02 보고서에, Claude의 실제 피드백은 07 원문에 보존했다. 내 수정안은 이 피드백을 근거와 반례로 검토해 작성한 의견이다.
